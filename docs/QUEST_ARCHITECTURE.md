# クエスト・報酬・演出 拡張方針

更新日: 2026-08-15  
状態: Approved direction

実装同期: PR #8で内部イベント、JSON定義パック、進捗評価器、初回達成記録、報酬受取台帳の基盤を追加。PR #9でミッション・報酬状態のUIを接続。PR #10でボーナスXPの一度だけの実付与と保存可能な達成演出キューを接続。

## 1. 目的

トレーニング記録を壊さず、デイリー、ウィークリー、チャレンジ、イベント、隠し実績、報酬、キャラクター演出を段階的に追加できる構造を定義します。

## 2. 責務の分離

| 領域 | 責務 | 扱わないもの |
|---|---|---|
| トレーニング | 種目選択、実行、回数・時間、タイマー、セット記録 | 報酬条件の個別判定 |
| クエスト | 記録に対する条件判定、進捗、期限、達成状態 | セット記録そのものの変更 |
| 報酬 | XP、称号、アイテム等の付与と重複防止 | 達成条件の計測 |
| 演出 | キャラクター反応、スタンプ、紙吹雪、宝箱等の表示 | 記録・報酬の確定 |

演出を中断してもトレーニング記録と報酬確定は失われない構造にします。

## 3. 画面構成

既存のクエスト領域を、次の2区分で実装します。

1. **今日のメニュー** — 種目選択と当日セット進捗
2. **ミッション・報酬** — デイリー、週間、イベント等の進捗と受取状態

トレーニング実行画面は上記から遷移する独立画面とし、ミッション表示を重ねません。

## 4. クエスト種別

- `daily` — 当日中のセット数、カテゴリ、種目完了
- `weekly` — 実施日数、週間セット数、複数カテゴリ達成
- `challenge` — 秒数、連続日数、特定メニュー完遂
- `event` — 開催期間を持つ限定条件
- `achievement` — 期限のない累積・隠し実績

## 5. データ定義

クエストは画面や判定処理へ直接書き込まず、安定したIDを持つ定義データとして管理します。

```json
{
  "id": "daily_complete_3_sets",
  "type": "daily",
  "metric": "completed_sets",
  "target": 3,
  "filters": {},
  "reward": { "xp": 20 },
  "presentation": {
    "title": "デイリー3セット",
    "tier": "standard",
    "media": { "imageUrl": null, "audioUrl": null },
    "trainerDialogue": { "default": "3セット達成！" }
  }
}
```

表示文言、条件、報酬、演出等級を分離し、既存クエストのIDは公開後に再利用しません。

### 5.1 パック配置

- コア定義: `data/quests/core.json`
- スキーマ版: `schemaVersion: 1`
- パックID: `packId`
- 定義配列: `quests`

HTMLへ個別クエストを書き足さず、JSON内の定義追加で拡張します。公開済みのクエストIDは意味を変更せず、条件を作り直す場合は新しいIDを発行します。

### 5.2 画像・音声・台詞

各定義の `presentation` に以下の差し替え口を持たせます。

- `media.imageUrl` — 達成カードや説明画像。未使用時は `null`
- `media.audioUrl` — 効果音・短い音声。未使用時は `null`
- `trainerDialogue.default` — 共通台詞
- 将来のキャラクター別台詞 — `trainerDialogue.rio` 等を追加可能

実行時に使う軽量素材はGitHub上の相対URLまたは配信可能なHTTPS URLを指定します。Google Driveは制作原本の保管先とし、Driveの共有画面URLをランタイム参照には使いません。

### 5.3 初期定義

`core_quests_v1` は次の5件から開始します。

- デイリー: 最初の1セット、合計3セット、体幹2セット
- ウィークリー: 実施3日、合計12セット

報酬値は定義データから読み取り、画面上は進行中、達成済み、受取済みを区別します。達成済みカードの受取操作でのみ実付与し、同じクエスト期間の受取台帳が存在する場合は再付与しません。

## 6. イベント処理

処理順序を次に固定します。

1. セット完了等のトレーニング記録を保存
2. `training:set-completed` 等の内部イベントを発行
3. クエスト進捗を再評価
4. 初回達成を保存
5. 報酬を一度だけ確定
6. 表示待ち演出をキューへ追加
7. ユーザー操作可能な時点で演出を再生

進捗は既存のトレーニング履歴から再計算できるものを優先し、保存値との不整合を減らします。

PR #8では1〜4までを実アプリへ接続し、5の重複防止用台帳APIを用意しました。PR #9では進捗・達成と受取台帳状態をUIへ接続しました。PR #10では5〜7を接続し、受取台帳、ボーナスXP、演出待ちを1回の `muscleMasterStateV2` 保存へ確定します。セット取消や当日リセット時も現在進捗は下げますが、一度成立した達成記録と受取済み報酬は消去しません。

演出キューの先頭は、ユーザーが報酬カードの「続ける」を押すまで保持します。再読み込みで未確認演出を再表示しても受取台帳が先に存在するため、XPは再付与されません。報酬によってレベル閾値を越えた場合は、報酬カードを確認した後に既存のレベルアップ演出を表示します。

## 7. 演出等級

| 等級 | 用途 | 例 |
|---|---|---|
| `minor` | 小さな進捗 | スタンプ、短いトースト |
| `standard` | デイリー達成 | キャラクター反応、紙吹雪 |
| `major` | 週間・称号 | 報酬カード、宝箱、専用台詞 |
| `special` | イベント・隠し実績 | 専用背景、複合演出 |

`prefers-reduced-motion` を尊重し、演出を省略しても達成内容と報酬を文字で確認できるようにします。効果音OFF設定も引き継ぎます。

## 8. 保存データと互換性

- 現行の `muscleMasterStateV2` を直ちに変更しない
- クエスト導入時は、既存データへ任意項目として追加する後方互換移行を行う
- トレーニング履歴、累計セット、能力値をクエスト側から上書きしない
- 達成・報酬には一意な受取記録を持たせ、二重付与を防ぐ
- クエスト定義更新後も、公開済みIDの意味を変更しない

`muscleMasterStateV2` へ追加する任意項目:

```json
{
  "bonusXp": 0,
  "quests": {
    "schemaVersion": 1,
    "progress": {},
    "completions": {},
    "rewardClaims": {},
    "presentationQueue": []
  }
}
```

旧データに `bonusXp` または `quests` がない場合は、それぞれ `0` と空の状態を補います。既存の `days`、`totalSets`、`stats` はクエスト評価器から変更しません。総XPは `totalSets × 10 + bonusXp` として表示します。
